# Video Comprehension 视频理解插件

KiraAI 视频理解插件：自动检测 QQ 视频消息，压缩 + 三级抽帧 + 拼图分析；**语音转写**（B站官方字幕优先，模型自带音视频理解时可跳过）；支持 B 站链接下载/发送/搜索/AI 总结/**html5 直链直传**；4 组模型独立配置（原生视频 / 抽帧 / 自带音视频理解）；支持本地视频与时间段分析。

## 核心能力

1. **自动检测视频消息** — 递归扫描消息链（**含引用 `Reply.chain` / 合并转发 `Forward.chains`**，支持多层嵌套）→ `raw_message` → **按消息 ID 主动调 `get_msg` 拉取**三级兜底
2. **自动缓存收到的视频** — 检测到就立刻下载到本地，并在下一轮对话把路径告诉 bot（`auto_cache_video`，默认开；缓存范围由 `cache_scope` 控制，默认只缓存被 @/引用/唤醒的）
3. **语音转写** — 把视频里的声音转成**带时间轴的文字**一起交给模型（`native` / `frames` 两种模式都会带）；**B站官方字幕优先**；模型自带音视频理解时可一键跳过（`native_audio`）
4. **压缩管线** — ffmpeg 缩放 + CRF 压缩，保持时长不变
5. **三级抽帧** — 场景变化帧 → I 帧 → 均匀补帧，信息密度最大化
6. **拼图 + 时间戳标注** — 每帧标注 `MM:SS.mmm [I/P] #N`，多帧合成拼图，按时间顺序排列
7. **多模型路由** — 4 组独立配置（`frames` 与 `native` **严格隔离**，frames 组绝不会有 video_url），按优先级 + 时长自动选择；`native`（传视频）或 `frames`（传拼图）。**可以按名字指定**：「用 Agnes 抽帧分析」→ bot 传 `model="Agnes"` 即可
8. **会话管理** — 首轮分析 + 后续追问（`session_id`），新视频自动切换会话；**模型粘性**（追问默认沿用首次分析用的模型组）
9. **时间段分析** — bot 可指定只看第 N~M 秒，支持一次多段（最多 5 段、每段 ≤300 秒）
10. **B 站能力** — 链接自动下载发送（0 token）、搜索、AI 总结优先、按质量下载、html5 直链直传

## 自定义请求头 / 请求体（每组模型独立）

每个模型组都有两个 JSON 配置项，对应 OpenAI SDK 的 `extra_headers` / `extra_body`：

| 配置项 | 作用 | 示例 |
|--------|------|------|
| `extra_headers_N` | 合并进每次 API 请求头 | `{"X-Api-Version": "2024-01"}` |
| `extra_body_N` | 合并进请求体（厂商私有参数） | `{"enable_thinking": true, "thinking_budget": 4096}` |

常见用法：

- **Qwen3-VL 开思考模式**：`extra_body` = `{"enable_thinking": true, "thinking_budget": 8192}`
- **GLM 开深度思考**：`extra_body` = `{"thinking": {"type": "enabled"}}`
- **自定义网关鉴权**：`extra_headers` = `{"X-Api-Key": "xxx"}` 或 `{"Authorization": "Bearer xxx"}`
- **厂商私有采样参数**：`extra_body` = `{"top_k": 5, "seed": 42}`

行为说明：

- 字段为空 `{}` 或非法 JSON → 视作未配置（**不会因此报错**，只是不带）
- 直接写 dict 或写 JSON 字符串都能识别
- 这两个参数**不会覆盖** `model` / `messages` / `timeout` / `max_tokens` 这几个插件自己设置的字段（同名键以 extra_body 为准，所以别往这里写它们）
- `frames` 与 `native` 两条调用路径都已带上

## 上传换公开链接（给 GLM 这类只吃 URL 的模型）

智谱 GLM 官方示例里的 `video_url` 是**公网 URL**形式，base64 没有官方保证。开启后，native 模式会先把视频上传到文件中转服务，把返回的链接传给模型：

```
本地视频 → (单段则秒切) → 上传 → https://x0.at/xxxx.mp4 → 模型自行拉流
```

- **配置**：设置 → 视频上传 → `upload_enabled`（**默认开启**）、`upload_hosts`（默认 `litterbox` → `x0.at`，**前一个失败自动换下一个**）
- **压缩策略**（`upload_compress_over_mb`，默认 **20MB**）：≤该值**不压缩**直接上传（保住画质、少一次转码）；超过才压到 720p 再传。设 `0` = 全程不压缩

### 上传源对比（实测）

| 服务 | 上限 | 保留 | 匿名上传 | 国内可达（上传端） | HEAD |
|------|------|------|---------|-----------------|------|
| **litterbox.catbox.moe**（默认） | 1 GB | 1h / 12h / **24h** / 72h | ✅ | ✅ 46/49 | ✅ |
| **x0.at**（备用） | 1024 MiB | 3~100 天 | ✅ | ✅ 33/33 | ❌ 404 |
| catbox.moe | 200 MB | **永久** | ❌ `Invalid uploader` | ❌ 0/47 | — |
| 自建 filehost2 | 看配置 | 看配置 | ✅ | ✅ | 看配置 |

- **服务类型自动识别**（`detect_kind`）：`litterbox.catbox.moe` → litterbox 协议；`catbox.moe` → catbox 协议；其余按 filehost2 协议（x0.at / 0x0.st / 自建）
- ⚠️ catbox 主站**国内上传端全不通**（匿名上传直接被拒），所以没做默认；想用要自己有账号且网络能通
- litterbox 的链接是**临时**的（默认 24h 后失效），比 catbox 的永久存储更适合"传上去给模型看一眼就丢"
- **失败自动回退**：上传未启用/超限/失败 → 自动改用 base64 内联，不会因此失败
- **重复不重传**：同一文件（路径 + mtime）在本次运行内缓存 URL；x0.at 服务端还会按文件哈希去重
- **绕过体积限制**：base64 模式受 20MB 上限（超了降级帧模式），有 URL 时不受此限
- **链接会给 bot**：分析结果里带 `🔗 视频直链: …` 一行，bot 因此知道链接，可以直接分享给用户或后续引用；该链接同时存进会话，追问时仍能看到
- **音频不受影响**：上传只是换传输通道，文件完全一样（≤20MB 时甚至因跳过压缩而保持原始音频码率）
- **隐私**：⚠️ 上传后该视频可通过链接被**任何人**访问（链接随机但公开）。链接与文件保留 3~100 天（越大越短）。介意就不要开，或换成自建的 filehost2

实测：x0.at 国内电信 33 节点全部 200；litterbox 文件域 33/34、上传域 46/49；两者的**拉取方 UA 均无限制**（空 UA/各种客户端都 200）、都支持 Range、`content-type: video/mp4` 正确。

## 视频自动缓存（给 bot 直接用）

`auto_cache_video`（基础设置里，默认开）：检测到 QQ 视频就**立即下载到本地缓存**，并在下一轮对话注入一行提示：

```
【视频】《nya.mp4》(0.33MB) 已缓存到 files/video_analysis_cache/v1757…_nya.mp4，
可用 analyze_video(local_path="files/video_analysis_cache/v1757…_nya.mp4") 分析其内容
```

这样 bot 知道**有视频、在哪、怎么用**，不必自己去翻目录。

缓存受 `cache_max_file_mb` / `cache_ttl_hours` / `cache_max_total_mb` 三重约束（见上「缓存设置」），不会无限增长；下载是**边下边检测**，超限立刻中止并删掉半截文件。

**为什么需要这个**：KiraAI 框架在消息渲染阶段有这段判断（`core/message_manager.py`）——

```python
video_file_size = int(ele.size)
if not video_file_size or video_file_size > 10 * 1024 * 1024:
    message_str += f"[Video name: {ele.name} (Video size over 10MB, not cached)]"
```

`not video_file_size` 把**「体积未知」也算成「超过 10MB」**，而文案只提了 10MB —— 所以会出现「明明不到 1MB 却显示 over 10MB」的误导日志。

被引用消息（`get_msg` 返回）的 video 段**常常没有 `file_size` 字段**，于是框架**放弃缓存**，bot 只看到一行占位文本 —— 表现为「视频没有被缓存、bot 找不到也不好用」。

本插件的做法是**不依赖框架缓存**：自己递归找到视频、自己下载、自己把路径告诉 bot。框架那行日志仍会出现，但不影响使用。

## 缓存范围（`cache_scope`）

默认**只缓存「被 @ / 引用 / 唤醒」的视频**——群里与 bot 无关的视频不会被下载，省流量也省 ASR 费用。

| 值 | 行为 |
|----|------|
| **`mentioned`（默认）** | 只缓存被 @ / 引用 / 唤醒的消息里的视频 |
| `batch` | 缓存所有进入 bot 批次的消息里的视频 |
| `all` | 群里所有视频都缓存（最耗） |

**实现上的分界**：

```
on_im_message（每条消息）      → 只记录视频 URL（轻量、不下载）
        ↓
on_im_batch_message（批次确定要处理）→ 按 cache_scope 决定下载哪些
        ↓
bot 主动调 analyze_video        → 任何时候都能用（不受 cache_scope 限制）
```

> ⚠️ 最后一行很重要：`cache_scope` 只管"**要不要提前替你缓存**"，**从不限制 bot 主动分析**——工具调用永远能用（`bvid` 现下、`local_path` 直读、无参数则用最近缓存的视频）。

### bot 自己发的消息不会触发

插件会跳过 **bot 自身发的消息**（`self_id == sender.user_id`，或 `raw_message.post_type == "message_sent"`）——不会自动发送、也不会当"收到的视频"缓存。

原本这靠两层外部默认值兜着：

1. SnowLuma / NapCat 的 `reportSelfMessage` 默认 `false`（不上报自身消息）
2. 自身消息的 `post_type` 是 `message_sent`，而框架只处理 `post_type == "message"`

但这两条都是**外部默认值**，万一被改或换实现，bot 自己发的B站链接就会被钩子再发一遍（重复刷屏）。所以插件自己再挡一道，不依赖外部配置。

> 效果：`send_video` 发出去的视频**不会**被自动钩子重新发一次，也不会被缓存/转写。

### B站链接的识别范围

自动发送（`auto_send_link`）**只认「明确的 B站链接」**：

| 形式 | 会不会触发 |
|------|:---:|
| `https://www.bilibili.com/video/BV…`（含带参数的） | ✅ |
| `https://b23.tv/xxxxxx` | ✅ |
| **QQ 小程序卡片**里的 `qqdocurl` 短链 | ✅ |
| **裸 BV 号**（如 `看看 BV1xx411c7mD`） | ❌ **不触发** |
| 形似 BV 的普通字符串（如 `订单号 BV1234567890`） | ❌ 不触发 |

> **为什么不认裸 BV 号**：`BV` + 10 位字母数字在日常聊天里出现概率不低，很容易误触发；
> 而且如果是假号，会先请求 B站接口、拿回 `code=-400` 再报错。
> 需要发裸 BV 号的视频，让 bot 主动调 `send_video` 即可（工具不受此限制）。
>
> 卡片不是 `Text` 类型元素，所以插件扫描的是**每个元素的所有字符串字段**（含 dict / list），
> 不依赖具体元素类型 —— 适配器把卡片塞成 `Json` / `Unknown` 都能识别。

### 自动发送的报错不会发到会话里

自动钩子（`auto_send_link`）是后台行为，它的**失败与异常只写日志**，不会往群里/私聊发提示
（避免刷屏打扰）。要排查就看运行日志（cmd）里的 `[VC] auto_send …` 行。

`send_video` / `analyze_video` 这类**工具调用**不受影响——它们的错误会正常返回给 bot。

### 消息改写：bot 不会再误判"看不到视频"

KiraAI 框架在渲染消息时会写一句误导文本（体积未知就写成"超过 10MB 未缓存"）。插件会把它**改写**成准确信息：

| 情况 | bot 看到的 |
|------|-----------|
| 已缓存 | `[视频已缓存: files/video_analysis_cache/v1789348603_xxx.mp4]` |
| 缓存失败 | `[视频未缓存: 超过单文件大小上限]` |
| 未预缓存 | `[视频 x.mp4（未预缓存，可用 analyze_video 分析）]` |

最后一种保证 bot 即使遇到"没提前缓存"的视频，也知道**工具能处理**，而不是回答"我看不到内容"。

（`system prompt` 里另有一行简短的用法提示：`analyze_video(local_path="...")`）

## 视频获取的三级兜底

视频可能藏在各种地方，插件按顺序主动找：

| 顺序 | 来源 | 覆盖场景 |
|------|------|---------|
| ① | **递归扫描消息链** | 直接发的视频、**引用消息**（`Reply.chain`）、**合并转发**（`Forward.chains`）、以及多层嵌套（转发里套引用） |
| ② | `raw_message` 原始段 | 适配器没往链里塞、但原始结构里有 video 段 |
| ③ | **主动调 OneBot 接口** | 链和原始结构都没有时：先按当前消息 ID 调 `get_msg`，再按**被引用消息 ID** 调 `get_msg` |

第 ③ 步只在**确实有视频迹象**时才触发（链里出现过 Video / raw 里有 video 段 / 有未解析的引用元素），所以纯文字消息**不会**白跑一次 API 调用。

## 模式隔离（硬约束）

每个模型组的 `mode` 是**硬约束**：

| 配置 | 行为 |
|------|------|
| `frames`（抽帧） | **只传拼图**（image_url），永远不会传 `video_url` |
| `native`（原生） | 传视频；若失败会自动降级到 `frames`（单向，不会反向） |

为什么重要：`frames` 组往往是那些**只支持 `image_url`、不支持 `video_url`** 的模型（比如纯视觉模型）。一旦误走原生调用，要么直接报错，要么行为不可预期。

代码里有**双重保障**：
1. `_analyze_result` 只在 `profile.mode == "native"` 分支里调原生调用
2. `analyze_native()` 内部再做一次拦截 —— 传进来的 profile 若不是 native 模式，**直接抛错**，不会静默走错

> **例外**：`api_base` 是 `generativelanguage.googleapis.com` 时，`analyze_native()` 会**自动改走 Gemini 原生 API**（`generateContent` + `inline_data`）——因为它的 OpenAI 兼容层根本没有 `video_url`。这条路径同样只对 `native` 组开放，frames 组依然只会发拼图。

已用测试覆盖：frames 组在「全片 / 单段 / 多段 / 追问」四条路径下都只发 `image_url`，且直接调 `analyze_native` 会被拦截。

## 指定用哪个模型组

多个模型组同时启用时，**可以让 bot 按名字挑**：

1. 给每组填个「模型别名」（`label_1`~`label_4`），例如 `GLM` / `Agnes` / `快速`
2. 用户说「**用 Agnes 抽帧分析这个**」→ bot 调 `analyze_video(model="Agnes")`

匹配顺序：**别名 → 模型名 → 组号**（大小写不敏感，支持部分匹配，如 `glm` 能匹配到 `GLM`）。
传了不存在的名字时，返回值会**列出全部可用模型组**，bot 试一次就知道有哪些。

不指定 `model` 时行为不变：按 `priority` 升序 + 视频时长匹配 `max_video_sec` 自动选。

## 模型自带音视频理解（`native_audio`）

有些模型**自己能"听"**（原生音视频联合理解），对它们来说我们的 ASR 转写是**多余的**。所以每组都有个开关：

| 组 | 默认 | 说明 |
|----|------|------|
| 组1 GLM | **关** | GLM 的 `video_url` 只抽帧，听不到声音 → 需要 ASR 补 |
| 组2 **MiMo** | **开** | 原生全模态（图像/视频/音频/文本），自己会听 |
| 组3 **Gemini** | **开** | 走原生 API（`generateContent`）时音视频一起理解 |
| 组4 备用 | **关** | 视你配的模型而定 |

开启后：**bot 用本组分析视频时会跳过 ASR 转写**（省一次识别调用）。

> ⚠️ **只对"真的能听到音频"的模型开**。像 GLM、Qwen 这类只抽视频帧的模型如果开了，会连转写文字都没有 —— 等于把声音信息彻底丢掉，反而更差。
>
> 配置项里的原话：**使用本组可无需额外语音识别，如只用本组可直接关闭语音识别选项**
>
> 注意：**B站官方字幕不受这个开关影响**（字幕是文字，不是音频），照常使用。

## 语音转写（给模型补上"声音"）

### 为什么需要

多数"视频理解"模型（含智谱 GLM-5.3-Flash）的 `video_url` **只抽视频帧喂视觉编码器**，音频轨不被处理——模型的输入模态里根本没有独立音频。官方文档也印证：GLM-5.3-Flash 的输入模态是 `视频/图像/文本/文件`，`video_url` 参数定义里没有任何音频字段。

所以插件自己把声音变成**模型读得到的文字**：

```
视频 → 抽音轨 → 音频分析 → ASR 转写 → 带时间轴的文字 → 拼进提示词
                                                      ↓
              模型收到的 = 画面（视频/拼图） + 【语音转写时间轴】
```

### B 站下载：优先 html5 MP4（免合并）

B 站有两个取流接口，我们优先用 **`fnval=1 + platform=html5` 的 MP4 接口**：

| | DASH（原来） | **html5 MP4（现在优先）** |
|---|---|---|
| 下载 | 视频流 + 音频流**两个** | **一个文件** |
| 后续 | 需要 **ffmpeg 合并** | **不用合并** |
| Referer | 必须带 | **不用带** |
| 实测体积 | 11.1 MB | **7.7 MB** |

拿不到（接口变动/风控）会**自动回退 DASH**，不影响可靠性。

### B 站视频直链直传（`bili_direct_url`，默认开）

native 分析 B站视频时，直接用这条 html5 MP4 直链交给模型 —— **省掉一次上传**，视频也不用公开到图床：

```
B站视频 → 取 html5 MP4 直链 → 直接作为 video_url 交给模型
         （失败/取不到 → 自动回退上传，分析照常）
```

⚠️ **能不能成功取决于模型服务端拉流用的 User-Agent**。实测 B站 CDN 对这条直链：

| UA | 结果 |
|----|------|
| `Mozilla/5.0` / `Go-http-client` | ✅ 200 |
| 空 UA | ❌ 403 |
| `python-requests` | ❌ 403 |

所以**试不通就把它关掉**（会回退上传）。这条直链**会**写进结果的「🔗 视频直链」，但带上明确的时效提示：

```
🔗 视频直链(B站临时): https://upos-sz-xxx.bilivideo.com/xxx-1-16.mp4?...
   ⚠️ 带签名，约 2 小时后失效；只能现取现用（反复访问不会延长有效期）。
      需要长期分享请改用 send_video 把视频发到QQ，或重新调用 analyze_video 取一条新链
```

> ⚠️ 注意：B站直链的时限是 URL 里 `deadline=` 那个**签名有效期** —— 到点服务端就作废，**反复访问无法延长**（不是"多久不碰就回收"机制）。所以要长期分享得用 `send_video`（发视频到 QQ），而不是想办法"保活"。

### B 站视频：官方字幕优先 ✅

B 站视频**优先用官方字幕**（CC / AI 字幕）——它有**精确到 0.01 秒的时间轴**、免费、而且**完全不用跑 ASR**（连音轨都不用抽）：

```
B站视频 → 取字幕轨（wbi 签名）→ 挑中文轨 → 下载字幕 JSON
                                              ↓
                          body: [{from, to, content}] → 时间轴文档
                                              ↓ 没字幕才回退
                                         音频识别（ASR）
```

- 开关：`bili_use_subtitle`（默认开）
- 语言：按 `zh-CN → zh-Hans → zh → ai-zh → zh-TW → en` 优先挑，也可用 `audio_language` 指定
- **AI 字幕需要 B站 Cookie**（「📺 B站配置 → Cookie」）；没 Cookie 时只有人工字幕的视频能拿到
- **不依赖 ASR 配置** —— 只填了 Cookie 也能吃到字幕

### 配置（用 ASR 时 3 项必填）

| 配置 | 说明 |
|------|------|
| `audio_stt_base_url` | OpenAI 兼容的 `/audio/transcriptions` 端点，如 `https://api.siliconflow.cn/v1` |
| `audio_stt_api_key` | API Key |
| `audio_stt_model` | 模型名，如 `whisper-1` / `FunAudioLLM/SenseVoiceSmall` |

**三项缺任意一项就自动跳过转写**（不影响视频分析本身）。

### 自定义请求头 / 表单字段

ASR 也支持自定义请求（同模型组那套用法）：

| 配置 | 作用 | 示例 |
|------|------|------|
| `audio_stt_extra_headers` | 合并进 ASR **请求头** | `{"X-Api-Version": "2024-01"}` |
| `audio_stt_extra_body` | 追加 **multipart 表单字段** | `{"temperature": 0, "language": "zh"}` |

⚠️ ASR 走的是 `multipart/form-data`（不是 JSON body），所以第二个是"**再往表单里塞几个字段**"。数值/布尔/对象会自动转成表单能接受的形式。插件自身的 `file` / `model` / `response_format` 等关键字段**受保护，不会被覆盖**。

### 时间轴怎么来（尽量不切块）

| 服务的返回 | 处理 |
|-----------|------|
| 带 `segments[]`（Whisper 系 / Groq / 本地 faster-whisper） | **用原生时间戳**，一次调用搞定 ✅ |
| 带 `sentences[]` + `begin_time`（阿里云系） | 自动识别毫秒并换算 ✅ |
| 词级 `words[]` | 按 1.2 秒间隔自动合并成句 ✅ |
| **只有纯文本**（如硅基流动 SenseVoice） | 自动降级：本地 VAD 切块逐段识别来补时间轴 |

返回值解析兼容面很宽：OpenAI 风格、阿里云风格、词级、纯文本、甚至裸字符串；时间单位（秒/毫秒）按字段名判断，再用音频实际时长做兜底校正。

### L2：非语音声音标注

`ffmpeg silencedetect` 扫出所有"有声段"，与 ASR 识别出的语音段求差集 → 标出**有声音但没人说话**的片段：

```
[00:02.100 → 00:05.400] 主角说他明天要去北京出差
[00:31.000 → 00:35.200] 【非语音声音】持续 4.2 秒，该段有声音但未识别出人声（可能是音乐/音效/环境音/杂音）
```

这样模型知道"那段时间不是空白，是有动静的"，而不是以为画面静止。不依赖任何额外模型，纯 ffmpeg 分析。

### 不卡顿的设计

| 措施 | 说明 |
|------|------|
| **提前跑** | 收到视频时就挂在"自动缓存"旁边**并行**转写，bot 真要分析时通常已算好 → 零等待 |
| **硬超时** | 分析时最多等 `audio_wait_sec`（默认 60 秒），超时就不带转写继续，**绝不卡住分析** |
| **落盘缓存** | 按视频特征缓存，追问/时间段分析**0 等待**，跨重启有效 |
| **并发切块** | 兜底切块时并发调用（限流 3），不是串行 |
| **全链路吞异常** | 未配置/网络失败/识别失败 → 静默跳过，主流程完全不受影响 |
| **块数封顶不丢内容** | 块数超过 `audio_max_blocks` 时**自动放大切块粒度合并**（而不是丢尾部），长视频内容照样完整 |
| **并发可调** | `audio_concurrency`（默认 5）。5 分钟视频：并发 3 约 38 秒、并发 5 约 23 秒 |

成本参考：抽音轨约 0.1~2 秒（只解码不重编码），有原生时间戳时**总共 2 次 ffmpeg + 1 次 HTTP**。

### 实测：不同时长会怎么处理（默认设置）

| 视频时长 | 有原生时间戳的 ASR | 只有纯文本的 ASR（走兜底切块，默认 `gap=2.5s`） |
|---------|------------------|------------------------------------------|
| 10 秒 | 1 次调用 | 1 块 → ≈3 秒 |
| 30 秒 | 1 次调用 | 1 块 → ≈3 秒 |
| 90 秒 | 1 次调用 | **2 块** → ≈3 秒 |
| 5 分钟 | 1 次调用 | **11 块** → ≈6 秒 |

`audio_gap_sec`（默认 **2.5 秒**）决定切块的粗细：**相邻语音段间隔小于它就并成一块**。

| 5 分钟视频 | 块数 | 耗时 |
|-----------|------|------|
| `gap=0.6`（每句一块） | 72 块 | ≈38 秒 |
| **`gap=2.5`（默认）** | **11 块** | **≈6 秒** |

调小 → 时间轴更精确但调用更多；调大 → 更快更省但时间轴变粗。默认 2.5 秒是"速度/成本优先"的取值（自然对话的句子停顿通常就在这个量级）。

⚠️ 长视频若兜底转写没在 `audio_wait_sec` 内跑完，**本次分析不带转写**，但转写会**继续跑完并落盘** —— 下次追问或对同一视频做时间段分析时**零等待命中缓存**。

## 时间段分析

让 bot 只看视频的某一段，不用把整片都喂给模型：

```
analyze_video(session_id="abc123", question="这里在说什么", start_sec=30, end_sec=45)
analyze_video(bvid="BV1xx...", start_sec=0, end_sec=20)            # 首次调用也能限定
analyze_video(session_id="abc123", segments=[[10,30],[100,130]])   # 一次多段
```

- **参数**：`start_sec` / `end_sec` 为数字秒（`end_sec=0` 表示到视频结尾）；多段用 `segments=[[起,止],...]`
- **帧密度自适应**：每 ~2 秒 1 帧，最少 6 帧；多段时每段配额 = `target_frames / 段数`，总帧数不会失控
- **复用已下载的视频**：对已有 session 做时间段分析不会重新下载；同时跳过全片压缩（只处理片段）
- **native 单段**：用 `-c copy` 秒切该片段（含音频）传给模型 —— 能听到这段的语音；起点会对齐关键帧，结果里标注实际范围
- **多段**：统一走帧模式，一次请求覆盖所有段，拼图按段分开并在底部标注「段N/M 起~止」
- **限制**：单段 ≤300 秒、最多 5 段，超出会提示分段；`end_sec` 超出视频时长会自动截断

## 模型接口能力（重要）

| 厂商 | OpenAI 兼容 `video_url` | 建议模式 | 说明 |
|------|------------------------|----------|------|
| 智谱 GLM | 官方示例为 **URL** 形式 | `native` 或 `frames` | 官方文档仅演示公网 URL；base64 视频未在文档中保证，失败会自动降级 `frames` |
| 阿里 Qwen (百炼) | ✅ 支持，另有 `fps` 参数 | `native` | 本地文件支持 Base64 上传 |
| 小米 **MiMo** | ✅ 支持（URL + base64 ≤50MB） | `native` | **原生理解图像/视频/音频/文本**，1M 上下文；接口 OpenAI 兼容，可直接配进模型组 |
| Google **Gemini** | ❌ **不支持 video_url**（官方只认 Files API 上传 / base64 内联 / YouTube 网址）| `frames`，或 `native`+**官方端点** | 填**官方端点** `generativelanguage.googleapis.com` 时本插件会走原生 API（`inline_data` 内联，等于"上传"）；填**第三方中转**时会明确失败并降级帧模式 —— **传 URL 会被静默忽略，模型会回答「没看到视频」** |
| 其他 OpenAI 兼容 | 视厂商而定 | `frames` 最稳 | `native` 失败会自动降级 |

**自动降级**：`native` 模式请求失败（厂商不支持 / 视频超过 20MB / 请求体过大）时，自动改用拼图帧模式重试，并在结果中标注 `native→frames`。

**例外**：`api_base` 填 `generativelanguage.googleapis.com` 时会**自动改走 Gemini 原生 API**（`generateContent` + `inline_data`），不走 OpenAI 兼容层——它的兼容层只有 `image_url`/`audio`，没有 `video_url`。

**体积限制**：`native` 会把压缩后的视频整体 base64（体积 ×1.33）塞进请求。超过 20MB 会直接走帧模式，避免请求被拒或超时。

## 异步与并发（v1.17.0）

### 为什么需要

框架对「一次工具调用」有全局超时（`bot_config.agent.tool_call_timeout`，默认 **60 秒**）。而一次视频分析要**几分钟**（下载 + 压缩 + 40 次抽帧 + 转写 + 模型响应），默认配置下必然被掐断，且掐断后中间结果白做。

### 怎么解决

| 层 | 做法 |
|---|---|
| **① 提交路径** | `analyze_video` 只做参数校验 + 建任务就立刻返回（毫秒级），**永不 await 分析体** |
| **② 计时干扰** | 分析重活（逐帧 ffmpeg、ffprobe、PIL 拼图、JPEG→base64）**全部移出事件循环**。⚠️ 这一层不能省：Python 事件循环是单线程的，一个 4 秒的同步阻塞会让**所有**协程的计时器都晚 4 秒（实测过），那样框架的工具超时照样会误伤 |
| **③ 软预算** | 插件自己算 `analysis_budget_sec`（默认 200 秒）。到点**不是失败**，而是转后台继续、结果照常交回；即使工具协程被框架取消，任务依然活着并最终发通告 |

**结论：本插件的时间尺度与框架的工具超时完全独立**，不需要去改框架配置。

### 交互长什么样

```
用户：@bot 看看这个 BV1xx411c7mD
bot：我看看这个，稍等～                      ← 立刻（提交时）
      …1~3 分钟后…
bot：《原神》4.2 前瞻直播，主要看点：…        ← 完成时（通告回灌后 bot 自己组织语言）
     想细看哪一段直接说。
```

- 提交时工具返回里会明确要求 bot：**「用一两句话告诉用户正在看，稍等」**，并**禁止猜测视频内容**（它还没看过）
- 完成时通告里会要求 bot：**用自己的语气讲结果**、不要提「系统通知/后台任务/任务号」、不要重发视频

### 并行

同一个群里连发多个视频 → 最多 `max_parallel_per_chat`（默认 3）个同时跑，其余排队。多个任务几乎同时完成时，结果会按 `notice_coalesce_sec`（默认 2 秒）**合并成一条通知**，不会连开好几轮对话刷屏。

### 配置（设置 → ⚡ 异步与并发）

| 配置 | 默认 | 说明 |
|------|------|------|
| `async_analyze` | **开** | 首次分析后台执行。关闭则工具等分析完再返回（会受框架工具超时制约，不建议） |
| `async_followup` | **关** | 追问也后台执行。追问复用内存拼图、很快，默认同步即可 |
| `max_parallel_per_chat` | **3** | 每会话同时进行的分析任务上限（**追问不计入**） |
| `max_parallel_global` | **6** | 全局上限，0=不限 |
| `queue_timeout_sec` | **600** | 排队上限，超时告知「未执行」（不静默丢失） |
| `analysis_budget_sec` | **200** | 软预算：到点转后台继续，不算失败 |
| `pipeline_hard_timeout_sec` | **0** | 硬上限：到点真取消，0=不设 |
| `notice_coalesce_sec` | **2.0** | 完成通知合并窗口 |
| `task_keep_minutes` | **30** | 任务记录保留时长 |

## 配置自动迁移（v1.17.0）

本次有两个默认值变动，为**不打扰已经手动改过的用户**，采用「只迁移从未修改过的项」策略：

| 配置 | 旧默认 | 新默认 |
|------|--------|--------|
| `bili_max_download_sec` | 600 | **1800**（30 分钟） |
| `audio_concurrency` | 5 | **10** |

机制要点：

- 判定条件是「**当前值 == 旧默认值**」**且**「迁移标记不存在」。因为框架在启动时会把配置里缺失的 key 补成默认值（`plugin_registry._ensure_plugin_config`），单看数值无法区分「用户改的 600」与「一直是默认的 600」，所以**必须带标记**（写在插件自己的数据目录 `config_migrations.json`）。
- **先写标记、后应用**：万一根标记写失败，宁可这次不迁移，也绝不会二次覆盖用户的手动修改。
- 写回用 `tmp + os.replace` **原子替换**，并只合并我们改动的字段（其他字段原样保留）。
- 任何一步失败都**只告警，不影响插件加载**。
